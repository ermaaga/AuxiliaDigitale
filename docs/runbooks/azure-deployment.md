# Runbook — Azure deployment (H-03, ADR 0022)

Infrastructure in `deploy/azure/` (Bicep), provisioned by `.github/workflows/infrastructure.yml` (ADR 0024), images
built by ACR Tasks, releases by `.github/workflows/deploy.yml`. Commands by hand run from the repository root with
`az` logged in (`az account show`, subscription "Auxilia Digitale Production"). Secrets are read from standard input
or generated by the scripts, never typed on a command line.

| Resource group | Content |
|---|---|
| `rg-auxilia-next-shared` | VNet, `cae-auxilia-next-01`, `psql-auxilia-next-01`, `acrauxilianext01`, `kv-auxilia-next-shared`, RabbitMQ `ca-auxilia-rabbitmq-01`, Valkey `ca-auxilia-valkey-01`, job `caj-auxilia-psql-01`; satellite apps `ca-auxilia-openwa-01`, `ca-auxilia-agent-openwa-01`, `ca-auxilia-site-01` and their storage `stauxilianextshared` (ADR 0022 §11) |
| `rg-auxilia-next-automation` | `id-auxilia-next-infra`, identity of the Infrastructure workflow (`deploy/azure/automation.bicep`) |
| `rg-auxilia-next-<env>` (one per `deploy/azure/environments/<env>.bicepparam`: `qa`, `prod`, …) | identities, `kv-auxilia-next-<env>`, `stauxilianext<env>`, `ca-auxilia-{api,web,worker}-<env>`, job `caj-auxilia-auxctl-<env>` |

## Rules
- **Tenant slugs never match between environments** (e.g. `demo-qa` in qa): Postgres, the SignalR backplane and the
  tenant roles are shared (ADR 0022 §2, findings C1–C2 in §10).
- `redis-connection` always keeps `defaultDatabase` and `channelPrefix` (ADR 0022 §10, C3–C4); never copy the
  Data Protection keys of the prod Catalog into qa (C6).
- The key `dataprotection-kek` of each vault (ADR 0023) protects every secret of that environment: never delete it nor
  disable a version of it; rotating it (`az keyvault key rotate`) keeps the old versions enabled.
- Watch the metric *Active connections* of `psql-auxilia-next-01` during the first weeks of qa: B1ms has about 50
  connections for both environments (C7).
- Preview every change: Infrastructure workflow with *what-if* (or `deploy/azure/scripts/deploy.sh <shared|env> --what-if`).
- A template change keeps the running images (the scripts pass the current tag); images change only through a release.
- After a secret changes, restart the revisions that read it (`az containerapp revision restart`, or a new release):
  Key Vault references are resolved when a revision starts.

## First setup (once)
1. **Identity of the workflow** (an Owner of the subscription, once):
   `az deployment sub create --name auxilia-next-automation --location italynorth --parameters deploy/azure/automation.bicepparam`
   → outputs `clientId` (and `principalId`). It creates `rg-auxilia-next-automation/id-auxilia-next-infra` with
   Contributor + Role Based Access Control Administrator (limited to the roles of the templates) on the subscription
   and the federated credential of the GitHub environment `infrastructure`.
2. **GitHub** (Settings → Environments / Secrets and variables → Actions):
   - repository variables `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID` (`az account show --query "{tenant:tenantId, subscription:id}"`)
     and `AZURE_OPERATOR_OBJECT_IDS` (object ids of the people who will run `secrets.sh set`, separated by commas:
     `az ad signed-in-user show --query id -o tsv`);
   - environment `infrastructure` with a **required reviewer**, variable `AZURE_CLIENT_ID` = `clientId` of step 1;
     optional secret `ACR_TASK_GITHUB_TOKEN`: fine-grained token on `ermaaga/AuxiliaDigitale` with *Contents: read* and
     *Webhooks: read and write* (the workflow then creates/updates the ACR Tasks; otherwise run
     `deploy/azure/scripts/acr-task.sh < token.txt` by hand and delete the file);
   - environments `qa` and `production` (`production` with a required reviewer); their `AZURE_CLIENT_ID` comes in step 3.
3. **Provision qa**: Actions → *Infrastructure* → *Run workflow* with `environment = qa` (first with *what-if* if in
   doubt). The run deploys the shared resources, generates the secrets, creates RabbitMQ, Valkey and the psql job,
   the qa core (identities, Key Vault, storage), its connection strings and its Postgres login + Catalog database.
   The summary shows the `AZURE_CLIENT_ID` to set in the GitHub environment `qa`.
4. **Images**: `git push origin main:qa` — the push starts `auxilia-build-qa`
   (`az acr task list-runs -r acrauxilianext01 -o table`); the images are tagged with the commit SHA.
5. **Applications of qa**: *Infrastructure* again with `environment = qa` and `image = <sha>`; the summary shows
   `apiUrl` and `webUrl`. From then on releases go through `deploy.yml`.
6. **Catalog and first users** (job `caj-auxilia-auxctl-qa`, see "auxctl" below): `migrate catalog`, then
   `clients add --client-id web-bff --name "Tenant web" --type WebBff --origin <webUrl>` and
   `clients add --client-id console --name "Console" --type PlatformConsole --origin <webUrl>`; read the printed secrets
   from the job log and store them with `secrets.sh set qa web-client-secret` / `console-client-secret` (standard
   input); restart the web revision. Then `platform users add --email … --name …` (activation token in the log).
   **Check the Data Protection keys** (ADR 0023): after the first start every row of `catalog.data_protection_keys`
   must be encrypted with the vault key — in `psql` (job `caj-auxilia-psql-01` or the auxctl job)
   `SELECT friendly_name, xml LIKE '%AzureKeyVaultXmlDecryptor%' AS protected FROM catalog.data_protection_keys;` shows `true`
   on every row. A `false` row means `DataProtection__KeyVaultKeyId` did not reach that container: fix it and plan a new
   key ring before storing real secrets.
7. **Tenant documents**: in the console set `documents.storage.provider = azure-blob` with the connection string of
   `stauxilianext<env>` and container `documents` (the container disk is ephemeral; `local` loses the files).
8. Repeat 3, 5–7 for `prod` (a `git push` to `main` builds `auxilia-build-main`; GitHub environment `production`).

The shell route still works with the same rights (`az login` as Owner, or the workflow's rights):
`deploy/azure/scripts/provision.sh <env> [--image <sha>] [--what-if]` runs the same steps.

## New environment (demo, dev, …)
1. Add `deploy/azure/environments/<name>.bicepparam` (copy `qa.bicepparam`): `environmentName` = `<name>` (2–9
   lowercase letters/digits, not `shared`), `githubEnvironment` = `<name>`, a `valkeyDatabase` no other environment
   uses (0–15), retention and replicas. Merge it to `main`.
2. *Infrastructure* with `environment = <name>`: shared resources updated (new Postgres password, RabbitMQ user and
   vhost — the broker restarts —, psql job), then the new environment.
3. GitHub environment `<name>` with the variable `AZURE_CLIENT_ID` from the summary.
4. *Infrastructure* again with `image = <sha>` (images of `main` or `qa`), then steps 6–7 of the first setup.
   Releases: *Deploy* → *Run workflow* with environment `<name>` and the SHA (only `main` and `qa` release by
   themselves). Tenant slugs of the new environment never match those of the others.

## Template change
Merge the change, then *Infrastructure* (with *what-if* first) for each environment; the shared part is applied by
every run. Running images are kept.

## Satellite apps
ADR 0022 §11; after the first *Infrastructure* run (`openwa-api-key` exists). The workflow keeps their running tags.
- set ports, session folder and settings in `deploy/azure/shared.bicepparam` (`openwaPort`, `openwaEnv`, …);
  secrets of the agent: `secrets.sh set shared <name>` + `agentOpenwaSecrets`;
- one ACR Task per repository, e.g. `deploy/azure/scripts/acr-task.sh satellite site <owner/repo> main < token.txt`
  (token with *Contents: read* and *Webhooks: read and write* on that repository); a push builds
  `auxilia/<app>:<sha>`;
- `deploy.sh shared --openwa <sha> --agent-openwa <sha> --site <sha>` (each one optional); the site URL is the
  output `siteUrl`, OpenWA's internal URL `openwaInternalUrl`;
- OpenWA: link the WhatsApp number once (QR code from the logs: `az containerapp logs show -g
  rg-auxilia-next-shared -n ca-auxilia-openwa-01 --follow`); the session stays on Azure Files.

## Release
Push to `qa` → CI green → **Deploy** releases to qa. Merge to `main` → CI green → **Deploy** waits for the reviewer of
`production`. Steps: wait for the four images of the commit → `auxctl migrate catalog` → `auxctl migrate tenants --all`
→ update worker, api, web → `GET /health/ready` → automatic rollback of the applications if anything fails after the
migrations. A failed migration stops the release with the previous version running (`MigrationFailed` tenants:
`docs/runbooks/tenant-provisioning.md`).

**Satellite apps**: `deploy/azure/scripts/deploy.sh shared --<openwa|agent-openwa|site> <sha>` (manual; the other
apps keep their tags). Rollback = the same command with the previous SHA. OpenWA sleeps when unused and receives no
WhatsApp message while asleep.

**Rollback by hand**: Actions → Deploy → *Run workflow* with the environment and the previous commit SHA (migrations
are expand/contract, the older images run on the newer schema).

## auxctl and psql in the VNet
Postgres has no public endpoint; commands run as Container Apps jobs. The job keeps its environment and secrets; only
image and arguments change:

```bash
az containerapp job update -g rg-auxilia-next-qa -n caj-auxilia-auxctl-qa --args tenant list
az containerapp job start  -g rg-auxilia-next-qa -n caj-auxilia-auxctl-qa
az containerapp job logs show -g rg-auxilia-next-qa -n caj-auxilia-auxctl-qa --execution <name> --container auxctl
```

Commands that read a secret from standard input (`users verify-legacy-hash`, `legacy import` connection) are not run
this way: pass the value through a Key Vault secret referenced as an environment variable of a temporary job.
The next release sets the arguments back to `migrate …`.

## Logs and troubleshooting
- Application logs: console page `/platform/tenants/{slug}/logs` (daily files in `stauxilianext<env>/logs`, deleted
  after 14 days in qa and 180 in prod by the lifecycle rule `logs-retention`).
- Live console output (no Log Analytics): `az containerapp logs show -g <rg> -n <app> --follow`.
- Scale to zero: the first request after a pause wakes web, API, Valkey and RabbitMQ (10–30 s). The web app has one
  replica and keeps BFF sessions in memory: users idle beyond the cooldown sign in again.
- Check on qa that RabbitMQ really scales to zero with the Worker's KEDA rules
  (`az containerapp replica list -g rg-auxilia-next-shared -n ca-auxilia-rabbitmq-01`); if it stays awake, see
  ADR 0022 §4 for the fallback.

## Registry cleanup (Basic has no retention policy)
```bash
az acr run -r acrauxilianext01 --cmd "acr purge --filter 'auxilia/.*:.*' --ago 30d --keep 10 --untagged" /dev/null
```
